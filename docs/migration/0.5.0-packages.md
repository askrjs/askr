# 0.5.0 package migration index

Upgrade the coordinated package set together. Every candidate version is exactly `0.5.0`, with sibling runtime/peer ranges prepared for the `>=0.5.0 <0.6.0` line. Follow the [release order](../development/coordinated-release.md) and qualify normal packed installs before changing a consuming application. The [cross-package acceptance record](../development/0.5.0-api-acceptance.md) binds the exact source/artifact inventory and remaining release gates.

Each linked package review lists every retired name/path, its supported owner or local replacement, and the reason for each retained contract. The links below are fixed to the reviewed candidate source, so later documentation changes cannot silently change this migration record.

## Provider-session applications

Configure the provider engine once on the server. Its shared confidential-client flow owns callback exchange, session/renewal, CSRF and redirect safety; the browser receives an HttpOnly session cookie and a minimal identity snapshot. Bind SSR and SPA through [Core provider sessions](../guides/provider-sessions.md). Browser-held tokens and the Auth0 SPA SDK adapter have no compatibility shim.

Auth0, Apple, Microsoft and Google remain **pending live qualification** until [Auth #71](https://github.com/askrjs/askr-auth/issues/71) records each live-provider result. The approved 0.5.0 scope uses signed simulated-provider acceptance; it does not claim a live-provider pass.

## Consumer migration sequence

1. Replace removed names and paths using the owning package guide; migrate sibling source, docs and CLI templates before publication of the owning package.
2. Generate fresh starters and run SPA, SSR, SSG, API and MCP consumers against the same complete packed candidate set. A consumer of a single package from npm 0.4.x does not validate the 0.5 graph.
3. Regenerate Website API data from the installed candidate declarations and check both public type acceptance and deliberate removed-import rejection fixtures.
4. Read back exact hosted checks, changelogs and artifact identities through the release coordinator. Keep #745/#747 open for any unsupported acceptance condition and #744 open through actual publication/readback.
